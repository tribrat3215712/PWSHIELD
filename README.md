# PWSHIELD

Исходники серверного патчера и runtime PZShield Core 1.1.1 для Project Zomboid. Изменения относятся к очередям, освобождению сетевых буферов и проверке физики транспорта. Целевая версия — **Build 42.21, ревизия `4a0e9546ec`**, проверенная по байткоду исходного `projectzomboid.jar`. Для другой версии требуется заново проверить и собрать патчи.

В репозитории находятся собственные Java-исходники, тесты, конфигурация и скрипты сборки. Для сборки нужен локальный JAR игры с указанной ниже контрольной суммой и JDK 25. Полученный серверный JAR будет создан в `dist/projectzomboid.jar`.

## Что обнаружено в присланном архиве

В архиве `java-4.zip` находились JAR, два Lua-файла и конфигурация PZShield. В JAR отсутствовали классы PZShield и ссылки на его настройки. Поэтому наличие конфигурации не подтверждало работу заявленных в ней механизмов. Конфигурация ссылалась на 42.20 и другой SHA-256; сам JAR содержит 42.21. Это не устанавливает, какие другие изменения ранее были внесены в игровые классы.

Исходный архив и распакованные файлы сохранены. Новая сборка изменяет четыре игровых класса; содержимое всех остальных записей JAR проверено на полное совпадение с присланным файлом. `serialize.lua` и `stdlib.lua` также сохранены без изменений.

## Реализованные изменения

- **Очереди сервера.** Каждый проход извлекает конечный FIFO-префикс. Новые поступления не продлевают текущую фазу бесконечно. Перед обработкой следующего пакета проверяется бюджет времени; необработанный хвост возвращается перед более новыми поступлениями. Это действует для HIGH, PLAYER и VEHICLE.
- **Физика транспорта при перегрузке.** Старый путь выбрасывания извлечённого хвоста отключён при включённом новом планировщике. Оставшиеся пакеты сохраняются на следующий проход. Каждая непустая фаза обрабатывает минимум один пакет, чтобы транспорт не останавливался навсегда из-за загрузки других очередей.
- **Память входящих пакетов.** Лимит резервируется до выделения буфера и остаётся занят, пока пакет находится в очереди или извлечённом списке. По умолчанию общий предел — 64 МиБ, на GUID — 8 МиБ. При превышении отключается отправитель. Размер учитывает ёмкость буфера и 128 байт на служебные структуры; это не предел всей памяти JVM.
- **Освобождение буферов.** Обработка пакета завершает возврат буфера через общий блок cleanup, включая ранний выход при исчезнувшем соединении и исключения. Необработанный хвост извлечённого списка восстанавливается после исключения; при выключенном планировщике выброшенные штатным кодом пакеты освобождают резервирование памяти. Обработанный элемент удаляется из списка до вызова обработчика, чтобы повторно используемый буфер не освобождался дважды. Пул хранит максимум 4096 свободных буферов по 2048 байт. Для больших пакетов выделяется фактический размер оставшейся полезной нагрузки вместо размера с заголовком.
- **Проверка входа.** Пустые и обрезанные сетевые заголовки отбрасываются до чтения. Неизвестные игровые типы блокируются до выделения сетевого буфера. Клиентские типы без серверного обработчика не ставятся в очередь.
- **Проверка физики машины.** До выделения буфера проверяются длина пакета, конечность чисел, индекс передачи и количество колёс: в этой версии игры массив рассчитан на четыре колеса. Дополнительно отклоняются quaternion с нулевой, переполненной или ушедшей в ноль при вычислении нормой. Перед изменением состояния проверяется ёмкость массива конкретной машины. Пакет без штатного права управления машиной не меняет её скорость и не передаётся остальным клиентам.
- **Штатная авторизация.** Проверка пакетов до входа, роли, capabilities и существующий античит сохранены в серверном потоке. Проверка Login не переносится на поток приёма: это могло бы отклонять корректные пакеты, ожидающие обработки после Login.
- **Телеметрия.** Отдельный daemon-поток пишет накопительные счётчики и состояние памяти в CSV раз в пять секунд. CSV ротируется при 10 МиБ; сохраняются текущий и один предыдущий файл. Логирование не выполняется для каждого атакующего пакета.
- **Опциональный ограничитель частоты.** Реализованы token bucket для пакетов и байтов по GUID, ограниченное число состояний и TTL. По умолчанию частотные пороги равны нулю, enforcement отключён. Численные PPS нельзя обоснованно выбрать по одному JAR без трафика сервера.

Сетевой бюджет по умолчанию — 70 мс. HIGH может занимать первую половину, PLAYER — время до 80% бюджета, VEHICLE — оставшееся время. Свободное время предыдущей фазы может использовать следующая. Один медленный обработчик всё равно может превысить бюджет: он не прерывается посреди изменения игрового состояния.

При ограничении по времени пакеты сохраняются, но могут обрабатываться позднее. Размер очереди ограничен настройками памяти. Это уменьшает конкретный источник потери обновлений транспорта; общий рассинхрон и производительность мира требуют проверки на реальном сервере.

## Установка готовой сборки

1. Собрать JAR по инструкции «Сборка из исходников». Остановить сервер и сохранить резервную копию его `projectzomboid.jar` и текущей конфигурации.
2. Заменить серверный JAR файлом `dist/projectzomboid.jar`. Для обычного Dedicated Server путь — `java/projectzomboid.jar` внутри папки сервера.
3. Положить **новый** `pzshield.properties` рядом с заменённым JAR. Старый конфиг содержит настройки несуществовавших в присланном JAR механизмов; использовать его как описание этой сборки нельзя.
4. Если конфиг уже существует в рабочей папке сервера, явно выбрать новый: добавить `-Dpzshield.config=java/pzshield.properties` к аргументам Java перед `-cp` в запускном BAT-файле. При другом расположении указать соответствующий путь. Сам запускной файл и параметры JVM здесь не изменяются.
5. Запустить сервер обычным способом. В консоли должна появиться строка `[PZShield 1.1.1] compiled hooks loaded`. Метрики по умолчанию записываются в `logs/pzshield-performance.csv` относительно рабочей папки.
6. На отдельном мире проверить вход и переподключение, поездки нескольких игроков, смену водителя и права управления машиной, инвентарь и активные моды. Сравнить исходный и новый JAR при одинаковой нагрузке.

Откат — остановить сервер и восстановить исходный JAR. Эта сборка не была автоматически установлена в Steam и не меняла сохранения пользователя. Скрипт копирует два локальных исходных Lua-файла в `dist` без изменения.

## Настройки и метрики

`queues.maxBufferedBytes` и `queues.maxConnectionBytes` задают квоты сетевых буферов, а не нормальную частоту игровых пакетов. Для очень больших модовых пакетов или значительного онлайна квоты следует проверить по `backlog_bytes`, `peak_backlog_bytes` и `memory_disconnects_total`.

Для включения частотного enforcement заполнить одновременно rate и burst нужного измерения и выставить `rateLimits.enforce=true`. Превышение отключает отправителя. Состояние ограничителя сохраняется при повторных вызовах для того же GUID до TTL; смена GUID создаёт другое состояние. При переполнении таблицы новые GUID пропускаются с увеличением `rate_state_overflow_total`, а квоты памяти продолжают действовать.

`deferred_*_total` считает события откладывания: один пакет может попасть в счётчик несколько раз. `network_cycle_ns` — время сетевых фаз, а не полный тик мира. `vehicle_owner_rejected_total` может расти при запоздавших пакетах после смены права управления; это не автоматический бан.

Настройки watchdog исходящих буферов, relevance-фильтра и coalescing из старого файла не реализованы в этой сборке. Новый файл содержит параметры реально используемого кода.

## Проверки и ограничения результата

Пройдено более 120 тысяч проверок. В сборку входят тесты FIFO и конкурентного поступления, остановки по бюджету, восстановления списков после исключений, реального пула `ZomboidNetData`, квот, отключённых режимов, конфигурации и ротации CSV. Отдельные интеграционные тесты используют настоящие игровые Reader/Writer, JOML, авторизацию `BaseVehicle`, `parse` и `processServer`. Независимый стресс очередей обработал 3 840 000 элементов без потерь и нарушения порядка внутри каждого производителя.

Четыре изменённых класса прошли анализ ASM и загрузку с `-Xverify:all`. Для всех остальных записей JAR проверено совпадение исходных байтов.

Исходный и исправленный Dedicated Server запускались локально на отдельных мирах с игровыми ресурсами и нативными библиотеками. Исправленный сервер принимал соединение настоящего RakNet-клиента, отклонял повреждённые игровые пакеты и сохранял мир. Подробности, результаты завершения и границы проверки находятся в `RECHECK_REPORT.md`.

Указанные в отчёте пути `audit/live` относятся к локальному проверочному стенду. Его логи, миры, игровые ресурсы и нативные библиотеки в репозиторий не входят.

**Полный игровой клиент, поездки нескольких игроков, моды и нагрузка с реальным онлайном не проверены.** Улучшение FPS, отсутствие всех видов рассинхрона или обнаружение всех читов этими проверками не доказаны. Внешний UDP-трафик до Java и нативные очереди не входят в квоту PZShield.

## Сборка из исходников

Нужен JDK 25. Исходный JAR должен иметь SHA-256:

```text
e1a69eb743ede60b213a0fe7f8b83d4fcab773036d256cc4543a336f3b058a33
```

Положить его в `original/projectzomboid.jar`, два исходных Lua-файла — в ту же папку. Затем:

```powershell
.\fetch-tools.ps1
.\build.ps1 -JdkPath 'C:\Path\To\JDK25'
```

`fetch-tools.ps1` получает ASM 9.8 из Maven Central и проверяет SHA-256 каждого файла. `build.ps1` очищает каталоги сгенерированных классов, компилирует hooks, применяет патчи к точному входному JAR и запускает тесты против полученного кандидата. Готовый JAR публикуется в `dist` после успешных проверок. Патчер сначала пишет временный файл, проверяет его и заменяет выходной JAR атомарно; он отказывается изменять входной JAR с другой контрольной суммой.

Документация используемых инструментов: [ASM](https://asm.ow2.io/documentation.html), [CFR](https://www.benf.org/other/cfr/). Декомпилированные игровые исходники использовались только для локального анализа; репозиторий содержит собственный код PZShield, патчер и тесты.
